# Terraform AWS onboarding

Status: implemented; ready for controlled testing; live customer validation outstanding
Last updated: 2026-10-06
Owner: Platform
Parent: ../../../core/specs/onboarding/aws-powershell-onboarding.md
Approval required: No — requested implementation.

## Decision

Add Terraform modules for AWS onboarding, equivalent to `terraform-azurerm-spotto` for
Azure. They consume the same portal setup package and return the same results JSON as
the PowerShell wizard, so the portal and API do not change.

Rejected alternative: generating IAM policies in HCL from purposes and billing inputs.
The parent spec rejected duplicating the API policy generator because drift caused
earlier onboarding gaps. The package keeps the API as the single policy author.

Naming: `terraform-aws-spotto` follows the `terraform-<provider>-<name>` convention
(`aws` is the AWS provider; `azurerm` is Azure's).

## Contracts

- Input: setup package V1 (`kind=spotto.aws.setup`), passed as JSON text.
- Output: results V1 (`kind=spotto.aws.manual-onboarding`): `companyId`, unchanged
  `configuration`, and one `{accountId, roleArn, status}` per enabled account. Status is
  `configured` after a successful apply. No External ID or credentials.
- Role tags: `SpottoCompanyId=<company>`, `SpottoManagedBy=Terraform`. The PowerShell
  wizard verifies such roles and refuses to adopt or change them.

## Behaviour

- One `account-role` per account and provider. Preconditions check caller account,
  package membership and partition before any IAM change.
- Inline policies are separate `aws_iam_role_policy` resources, so unrelated customer
  policies stay untouched and deselected Spotto policies are removed. Managed
  attachments depend on the inline policies (guardrails before broad reads).
- Existing roles fail with `EntityAlreadyExists` unless imported explicitly.
- Unlike the wizard, removing a module instance or running destroy deletes the role.
  This is documented as standard Terraform ownership.

## Risks

- Destroy deletes roles; mitigated by documentation and normal plan review.
- Guardrail S3 denies can block existing billing reads if the base prefix is wrong in
  the portal; documented as a pre-apply check.
- Static providers per account make large organizations verbose; StackSets, automatic
  organization discovery and billing export creation are deferred.

  offline suite (120 assertions) covers Terraform-tagged roles: verified without writes
  when matching; drift refused even with `-RepairExistingRole`.
